# 分段判据参考（Segmentation）

记录是逐字存的：每敲一下就是一条记录，内容是**输入框此刻的完整文本**。
"分段"要做的事，是把这些版本还原成人能读的"一段话"。

这份文档把全部判据集中在一处 —— 因为它们是本项目最微妙的逻辑，
散落在代码注释里时，改一处很容易忘掉另一处。

代码：`android/java/com/draftguard/Burst.java`
离线复现：`tools/merge_export.py`（同一套规则，可在电脑上验证）
测试：`test/BurstTest.java`（47 项，覆盖下列全部情形）

---

## 一、先分组，再合并

**关键点：排序键是「应用 + 输入框 + 时间」，不是只按时间。**

早期只按时间排序、逐条比对相邻记录，于是"打字中途切到别的应用"会把一段话切开：

```
[896] 12:51:35  appA  <这是一段比较长的示例文字用来演示>
[897] 12:52:40  appB  <示例短句>            ← 插在中间
[898] 12:53:06  appA  <这是一段比较长的示例文字用来演示，>
```

`mergeable()` 因"不是同一个应用"返回 false，一段话被拆成两段。
按「应用 + 输入框」分组排序后，同一输入框的记录必然相邻；合并完再按时间还原展示顺序。

## 二、合并判据（按顺序，命中即返回）

| # | 判据 | 结果 |
|---|---|---|
| 1 | 应用不同 | 分段 |
| 2 | **两条之间夹着一条「提交」记录**（`ev="send"`） | **分段**（真信号） |
| 3 | 输入框标识不同（两者都非空） | 分段 |
| 4 | 间隔超限：续写草稿用 `LONG_GAP_MS`，否则用 `GAP_MS` | 分段 |
| 5 | 两条都为空 | 合并（归并边界标记） |
| 6 | 一侧为空 | 分段 |
| 7 | 任意一方是另一方的开头（延伸 / 退格） | **合并** |
| 8 | `isFullRewrite` 为真 | 分段 |
| 9 | `isLocalizedEdit` 为真（且间隔 ≤ `LOCAL_EDIT_MS`） | **合并** |
| 10 | 共同开头 ≥ `MIN_COMMON_PREFIX` | **合并** |
| 11 | 间隔 ≤ `RAPID_EDIT_MS` 且两边都 ≤ `RAPID_EDIT_MAX` 且共用一个实义字 | **合并** |
| 12 | 其余 | 分段 |

## 三、阈值与理由

| 常量 | 值 | 为什么是这个值 |
|---|---|---|
| `GAP_MS` | 5 分钟 | 超过它、且看不出是同一段草稿，就当"另一段" |
| `LONG_GAP_MS` | 6 小时 | **接着写**未完成的草稿可以跨很久。用户实录：打完一段切出去办事，几小时回来接着打 |
| `KEEP_RATIO` | 0.5 | "整段重写"的判据：共同开头占较短串的比例低于它，且长度差够大 |
| `MIN_LEN_FOR_REWRITE` | 4 | 太短的文本（"嗯""好"）不做重写判定，避免误拆 |
| `MIN_COMMON_PREFIX` | 2 | 共同开头 ≥2 字才算"仍是同一条消息" |
| `RAPID_EDIT_MS` | 10 秒 | "整词打错重打"的时间窗 |
| `RAPID_EDIT_MAX` | 8 字 | 只有短内容才做"整词重打"判定 |
| `LOCAL_EDIT_MS` | 5 分钟 | "中间改一处"的时间窗 |
| `LOCAL_EDIT_MIN_PREFIX` | 3 字 | 判"中间改一处"所需的最短共同开头 |
| `LOCAL_EDIT_MAX_TAIL` | 4 字 | 分叉后两边剩余都 ≤4 字，就认为在改同一处 |

## 四、几个判据的来由（都对应一个真实反馈）

### 提交信号必须落盘，不能只放内存

最早把"用户点了发送"记在内存的静态字段里，判据是"这条记录之后有没有发送过"。
但那个时间戳是**内存中最后一次发送的真实当前时间** —— 用户一旦点过发送，
**所有更早的历史记录都被判成"发送之后"**，
实测表现为"QQ 1039 个版本合并出 1039 段"（一段都没合上）。

现在：检测到提交时写入一条 `ev="send"` 的记录（文本为空），
判据变成"两条文本之间是否夹着一条提交记录" —— 与当前时间无关、可复现、离线一致。

### 「接着写」可以用长间隔，靠提交信号兜底

判据 4 对"续写草稿"放宽到 6 小时。安全性来自判据 2：
**如果前一段真的发出去了，输入框会被清空**，
也就不会出现"新文本以旧文本开头"的形态。

### 整词打错重打（共同开头为 0）

用户实录（在设置里找一个选项）：

```
13:21:43  <甲苹果>
13:21:46  <乙苹果>      ← 3.4 秒后整词重打，共同开头 0
```

共同开头判据失效，故加判据 11：**短间隔 + 短内容 + 共用一个实义字**。
"实义字"排除了「的了吗呢是你我在」这类高频虚词 ——
否则 `你好呀` 与 `小朋友` 也会因个别虚词重合而误并。

### 局部改一处 / 中间改一处（分叉在字符串中间，`isLocalizedEdit`）

```
02:06:26  <…这是一个用来演示的示例句子>   →   02:06:28  <…这是一个用来演示的例子句子>
```

"新文本以旧文本开头"在这里失效（分叉在中间）。故加判据 9（代码里叫 `isLocalizedEdit`，即「局部改一处」）。

## 五、已知取舍（做不到的，写清楚）

| 情形 | 行为 | 原因 |
|---|---|---|
| 续打同一句 vs 发了一条相似的新消息 | 可能合并 | 文本层面同形；有提交信号时不受影响 |
| 连发两条很短的相似消息 | 可能合并 | 判据 11 的代价 |
| Compose 界面的提交（如 B 站发布） | 拿不到信号 | 该控件不产生逐按钮点击事件，只能靠文本判据 |
| 键盘回车/搜索键提交 | 拿不到信号 | 未订阅按键事件（需 `flagRequestFilterKeyEvents` + 受权） |

**排序原则：宁多不吞。** 合并错了只是分组粗一点（内容都在），
分段错了会让用户以为消息丢了。

## 六、怎么验证

```bash
# 离线复现（与应用同一套规则）
python tools/merge_export.py <解压目录> -o 汇总.md

# 排查"这两条为什么没合并"
python tools/why_not_merged.py <解压目录> <应用子串> <起> <止>
```

`why_not_merged.py` 会逐条打印每道判据的结果，是定位分段问题最快的办法
（判据 4 的"排序键"问题就是靠它发现的）。

## 七、面向用户的两个视图

存储永远保留**每一个版本**（崩溃恢复的前提）；界面提供两种读法：

| 视图 | 内容 | 用途 |
|---|---|---|
| **合并视图**（默认） | 每次连续输入只显示最后成型的整段 | 平时阅读 |
| **逐条视图** | 每个原始版本各占一条 | 排查"某条为什么不对" |

记录页有「看逐条 / 看合并」按钮切换。这是本项目的核心取舍：
**存储尽可能全，展示尽可能净** —— 不必为了可读性牺牲可恢复性。

## 八、分层原则（最重要的一条，取代一堆特例）

**过滤只作用于"显示"，不作用于"分段"。**

分段器（`Burst`）必须看到**完整**的记录流，包括：
- `ev="send"` 的发送标记
- 空文本的记录（输入框被清空）

这些"边界记录"没有正文、不该显示，但它们**是分段的唯一可靠依据**。
一旦在过滤阶段（`refreshList` 为了不显示空条目）把它们丢掉，
分段器就看不到任何边界，只能退回用文本形态去猜：前缀、共同字、间隔……
—— 而形态判据永远会漏，只能靠不断加特例来补。

**实测后果**：QQ 里逐条发送「好 / 好不好 / 你不好 / 你不会」四条独立消息，
界面合并成一条并标注"合并 4 版"。原因就是过滤把四条之间的发送标记全扔了。

**正确的分层**：

| 层 | 职责 | 对边界记录的处理 |
|---|---|---|
| 读取/过滤 | 按时间、应用、搜索词筛选 | **原样保留**（搜索时也保留，否则会跨过边界误合） |
| 分段（Burst） | 按判据把版本归并成"话" | 作为**第一优先**的判据使用 |
| 显示 | 逐条视图 / 合并视图 | `groupNewestFirst` 已负责把空段排除在结果外 |

判据的优先顺序也应按"证据强度"排，而不是按文本形态：

1. **两条之间夹着发送标记** —— 真信号，最强
2. **输入框被清空**（空文本记录）—— 结构性信号，几乎所有应用都有
3. **换了输入框或应用** —— 结构性
4. **间隔过长** —— 弱信号
5. 以上都没有时，才用文本形态（前缀 / 局部改字 / 整词重打）兜底

> 教训：**特例越加越多，是分层错了的信号。**
> 与其继续给判据打补丁，不如先问一句"我是不是把某个通用依据丢掉了"。
