# 一晚复盘：从搭环境到落地

记录一次真实开发过程（约 6 小时，从"应用一个字都记不到"到 7 个应用可用）。
重点不是"做了什么功能"，而是**哪些做法有效、哪些反复踩坑、时间花在哪了**。

---

## 一、起点与终点

| | 起点 | 终点 |
|---|---|---|
| 应用状态 | 无障碍服务收不到任何第三方应用事件 | **7 个应用**实测通过 |
| 调试手段 | 用户截图 + 口述现象 | ADB 直连：截图 / logcat / 模拟点击 / 拉文件，全自动 |
| 测试 | 无 | **74 项**离线断言（存储层 22 + 合并逻辑 36 + 占位判定等） |
| 提交 | 一个初始版本 | **24 个提交**，全部推送至 GitHub |

**最关键的转折点是一个决定**：花时间把 ADB 无线调试接通。

在接通之前，每一轮排查都是"用户截图 → 我读图猜原因 → 改代码 → 用户装包重试"，
一轮约 5–10 分钟，而且**经常猜错方向**（早期我连续两次把"没收到事件"误判成"解析逻辑有问题"）。

接通之后，一轮变成：读 logcat 看真实事件 → 精确定位 → 改代码 → `adb install -r` → 立刻复验，
**不需要用户参与**。后面 16 个 bug 里有 14 个是在接通之后解决的。

> 结论：**调试通道本身的价值，高于任何单个功能的开发速度。**
> 该花的钱是"把黑盒变成白盒"，不是"多写点功能"。

---

## 二、反复出现的一类 bug：**我"以为"的 API 行为不是实际行为**

这类问题占了全部 bug 的一半以上，且每次都表现为"逻辑看起来完全正确，但就是不对"。

| 我以为 | 实际 | 后果 |
|---|---|---|
| `event.getSource()` 会给出输入框节点 | 安卓 11+ 经常返回 `null` | 微信整块漏记 |
| `getRootInActiveWindow()` 能兜底 | 微信里同样返回 `null` | 兜底也失效 |
| 输入框节点 `isEditable()` 为真 | 有些应用（微信）返回 false | 节点被当成非输入框丢弃 |
| 输入框为空时 `getText()` 返回空、hint 单独给 | 小米笔记把 hint **通过 `getText()` 返回** | 提示文字被当成用户输入 |
| `isFocused()` 可靠 | 部分 ROM 会撒谎 | 焦点过滤可能反而不记 |
| `getApplicationLabel()` 能取应用名 | 安卓 11+ 包可见性限制下失败 | 界面显示包名 |
| `<receiver exported="false">` 只有 shell 能发 | **连 shell 都发不进去**（uid 不匹配被拒） | 诊断探针完全失效 |
| `renameTo()` 失败会抛异常 | 静默返回 false | 索引丢失，记录"看不见" |

**共性**：这些都是"框架文档里说得通、真机上不成立"的行为。

**应对方法（有效）**：

1. **先看原始数据，再改逻辑**。给应用加"原始事件环形缓冲"，把 `event.getType() + 包名 + 类名 + 文本`
   直接打出来。微信那次就是靠它一眼看出：事件里**一直带着完整文本**，而我把宝全押在节点上。
2. **不要用"再加一层兜底"来修**。我连续两轮都在放宽节点判定条件，方向是错的
   —— 因为节点根本拿不到。**当兜底越加越多时，说明对问题的理解是错的。**
3. **把假设写成断言**。"`你好呀我很.startsWith("你好呀我")`" 这条断言一跑就破除了
   我对"前缀延伸"的想当然。

## 三、时间花在哪：一个有欺骗性的统计

粗算这一晚：

| 阶段 | 大致占比 | 说明 |
|---|---|---|
| 打通 ADB 调试 | **~25%** | 配对码反复过期、adb 版本问题、MIUI 限制 |
| 定位真实根因 | ~20% | 但正因为有 logcat，这部分其实很快 |
| 写代码修 bug | ~10% | 真正的修复往往只有几行 |
| 写测试 + 被测试打脸 | ~20% | 我有 3 次是**测试期望写错**，不是代码错 |
| 与工具链搏斗 | ~15% | 构建脚本、PowerShell 怪癖、adb 限制 |
| 环境本身的问题 | ~10% | 代理、网络、版本不一致 |

**结论一**：**"改代码"从来不是瓶颈**。真正的修复基本都是几行。
时间全花在"搞清到底发生了什么"和"把环境弄通"上。

**结论二**：写测试的时间看着"浪费"，但至少三次避免了我把错误理解当成修复提交上去。

## 四、ADB 无线调试的坑（按踩到的顺序）

1. **配对码有效期极短**（几十秒）。"用户截图 → 我执行"必然失败，
   报错是 `protocol fault (couldn't read status message)`——看起来像协议不兼容，
   实际是**配对窗口已关闭**。最终解法是让用户在自己电脑上一条命令完成（零延迟）。
2. **PowerShell 管道传 stdin 给 `adb pair` 会失败**。`"配对码" | adb pair` 不会正确关闭
   stdin，adb 收不到 EOF。必须用 .NET 进程精确控制：写入后立即 `Close()`。
3. **adb 版本夹缝**：36.0.0 配对握手直接失败；29.0.6 又太旧、没有 `pair` 子命令。
   中途换 34.0.5 仍然失败——**最终证明不是版本问题**，是配对窗口过期。
   （教训：换版本前先确认失败原因，否则只是浪费时间下载。）
4. **`exported="false"` 连 shell 都发不进广播**。诊断探针第一版就是这么废掉的。
   正确做法：`exported="true"` + 应用内开关把门 + 明确文档说明。
5. **手机连的是电脑开的移动热点**（`192.168.137.x`），这反而比同一 WiFi 更稳，
   不受路由器 AP 隔离影响。
6. **应用私有目录 `adb pull` 不到**（Android 11+），非 debuggable 应用也不能 `run-as`。
   所以要看应用内部状态，只能让**应用自己**把它打到 logcat（探针方案）。

## 五、构建链的坑（不用 Gradle 的代价）

选择"只用 SDK 自带工具"是对的（APK 56KB、无依赖、构建几秒），但代价是一堆细节：

| 坑 | 现象 | 解法 |
|---|---|---|
| `sources.txt` 带 BOM | javac 报"无效文件名" | 用 `UTF8Encoding($false)` 写文件 |
| lambda 引导方法缺失 | `找不到符号: 方法 metafactory` | `core-lambda-stubs.jar` 进 bootclasspath |
| d8 输出目录不存在 | `Invalid output` | 先 `mkdir` 再喂 d8 |
| PowerShell 把工具 stderr 当异常 | 明明成功却中断 | 不用 `$ErrorActionPreference='Stop'` |
| Java 注释里的 `\u` | "非法的 Unicode 转义" | 注释里不写 `\u` |
| `org.json` 是空实现 | 离线测试报 `Stub!` | 自研 `Json.java` |
| 多行字符串替换失配（CRLF） | 替换静默失败 | 单行锚点 + **改完必须 `grep` 验证** |

最后一条尤其重要：**我在这一晚有 4 次"以为改了、其实没改"**，
都是因为 PowerShell 的 here-string 用 LF、而工程文件是 CRLF。
后来养成习惯：每次批量替换后立刻 `Select-String` 确认。

## 六、测试策略：为什么值得

**离线可测的前提是"不依赖安卓 API"**。为此做了两次抽取：

1. `Json.java`：替代 `org.json`（它在 `android.jar` 里是空实现，一碰就 `Stub!`）
2. `PlainText.java`：把"是不是占位提示文字"的纯字符串判定从 `TypelogService` 里搬出来
   （服务类一加载就 `Stub!`，没法离线测）

**测试抓到的真问题**：

- 搜索的 `limit` 被当成"每文件"上限用 → 整个文件被跳过（有回归断言）
- 输入框标识用 `identityHashCode` → 同一段文字被重复记录
- 合并逻辑用 `startsWith` 判"改错别字" → 完全失效（有断言固化这个反例）

**测试也抓到了我自己的错误理解**（3 次）：

- 把"追加"当成"替换"（`你好呀我` → `你好呀我很` 是长度 4→5 的追加）
- 把"删字"当成"不算修改"
- 一度以为 `isEdit` 有 bug，实际是我的测试用例构造错了

> 结论：**测试最大的价值不是防止回归，而是逼你把模糊的直觉写成明确的断言**——
> 而模糊的直觉正是这类 bug 的温床。

## 七、失败与无效的尝试（同样值得记）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 用 `adb shell input text` 输入中文 | 失败 | adb 只支持 ASCII；更糟的是它触发了拼音输入法状态，把输入框搅乱（需要善后） |
| 生成二维码给手机扫 | 失败 | `adb` 命令行没有生成二维码的子命令，那是 GUI 工具的功能 |
| 用 `--v1-signing-enabled true` 得到 v1 签名 | 实际只有 v2/v3 | 不影响（minSdk 26 只需 v2） |
| 反复换 adb 版本解决配对失败 | 无效 | 真正原因是配对窗口过期 |
| 靠截图 + 口述定位问题 | 低效且误导 | 早期两次方向性误判都源于此 |

**关于"输不了中文"这条**：这是 `adb` 的硬限制，但它带来一个意外好处——
**迫使我用 ASCII 做通路验证、由用户做中文验证**，反而分清了"链路问题"和"编码问题"。

## 八、可复用的方法论（如果只记 5 条）

1. **先修调试通道，再修功能。** 黑盒调试的成本是白盒的十倍以上。
2. **遇到"逻辑正确但结果不对"，去读原始数据**，别改逻辑。
   加一个"把原始输入打出来"的开关，几乎总能一眼看穿。
3. **重复加兜底 = 理解错了。** 停下来问："我最核心的假设是什么？它一定成立吗？"
4. **把假设写成断言。** 纯逻辑抽出来，离线跑；测试写错也是收获（说明理解偏了）。
5. **每次修改后立刻验证是否真的生效**（`grep` 一下）。静默失败的修改会浪费时间在错误的前提上。

## 十、后半程新增的教训（消息分段那一段）

前 3 小时解决的是"能不能记到"，后 3 小时解决的是"记到的东西怎么分组"。这一段的教训更值钱。

### 1. 最值钱的一次修正来自用户的观察，不是我的推理

我的分段逻辑改了两轮，都在"用文本形态倒推是不是发送了"这个框架里打转：
共同开头长度 → 清空边界 → 又回到共同开头长度。每轮都自洽，每轮都不对。

用户一句话点破：**"我点击的是微信的发送，你是不是记录不到"**

一查：确实记录不到 —— 我的无障碍服务只订阅了 `typeViewTextChanged|typeWindowStateChanged`，
**按钮点击事件根本没订阅**。真信号一直摆在那里没采集，我却在用文本猜了整整两轮。

**教训**：当你在用**间接特征**推断某件事时，先问一句"这件事本身有没有直接的信号？"
如果有，采集它；如果没有，再退回推断。我连问都没问过。

### 2. 同一个坑会换个地方再踩一遍

修微信文本时发现：`event.getSource()` 返回 null，所以要退回读 `event.getText()`。
写完这条，紧接着写"发送按钮检测"，**我又只从节点读标签，忘了读事件文本** → 检测恒为 0。

**教训**：在一个平台上总结出的"某类 API 不可靠"，要当成**该类 API 的普遍性质**去检查所有用法，
而不是只修当前那一处。

### 3. 测试全绿 ≠ 行为正确（这次最深的体会）

第 9 项测试原来断言的是："清空重打应合并成一段"。**我把错误的行为当成正确行为固化了下来，
测试还通过了。** 这个 bug 一直活到用户在真实聊天里用出来。

**教训**：测试验证的是"实现符合我的理解"，不是"我的理解符合需求"。
当实现和预期一致却仍有用户抱怨时，问题在预期，不在实现。

### 4. "首条文本即占位"这类兜底，来自观察而非想象

小米笔记、B 站的输入框占位文字有两种给法：`getHintText()` 单独给，或直接当 `getText()` 返回。
后者从文本上无法与真实输入区分。但有一个可靠性质：**占位文字一定是该输入框的首条文本**。
于是"首条文本记为占位候选"就成了通用兜底。

**教训**：找不到"内容上"的判据时，去找"时序上"的判据。

### 5. 记录能力 > 分组精细度（取舍）

B 站的「发布」按钮**完全不产生点击事件**（推测是 Jetpack Compose 界面，按钮是 Canvas 单节点）。
所以那类应用拿不到提交信号，分段只能退回文本形态。

但用户自己给出了正确判断：**"这种的话毕竟都在 b 站上保存了"** ——
内容本身完整记录，只是分组可能粗一点，而平台侧也有草稿。

**教训**：分清"核心目的受损"和"体验精细度不足"。后者不该用引入系统级权限去换。

**最值得保留的三样东西**（都不是功能）：
1. **诊断探针** —— 让应用内部状态可被外部读取，是后面所有远程排查的基础

> 一句话总结这一晚：**能看见，比能写代码重要得多。**
