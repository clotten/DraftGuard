# 一晚复盘：从搭环境到落地

记录一次真实开发过程（约 6 小时，从"应用一个字都记不到"到 7 个应用可用）。
重点不是"做了什么功能"，而是**哪些做法有效、哪些反复踩坑、时间花在哪了**。

---

## 一、起点与终点

| | 起点 | 终点 |
|---|---|---|
| 应用状态 | 无障碍服务收不到任何第三方应用事件 | **7 个应用**实测通过 |
| 调试手段 | 用户截图 + 口述现象 | ADB 直连：截图 / logcat / 模拟点击 / 拉文件，全自动 |
| 测试 | 无 | **74 项**离线断言（存储层 22 + 合并逻辑 36 + 占位判定等） |
| 提交 | 一个初始版本 | **24 个提交**，全部推送至 GitHub |

**最关键的转折点是一个决定**：花时间把 ADB 无线调试接通。

在接通之前，每一轮排查都是"用户截图 → 我读图猜原因 → 改代码 → 用户装包重试"，
一轮约 5–10 分钟，而且**经常猜错方向**（早期我连续两次把"没收到事件"误判成"解析逻辑有问题"）。

接通之后，一轮变成：读 logcat 看真实事件 → 精确定位 → 改代码 → `adb install -r` → 立刻复验，
**不需要用户参与**。后面 16 个 bug 里有 14 个是在接通之后解决的。

> 结论：**调试通道本身的价值，高于任何单个功能的开发速度。**
> 该花的钱是"把黑盒变成白盒"，不是"多写点功能"。

---

## 二、反复出现的一类 bug：**我"以为"的 API 行为不是实际行为**

这类问题占了全部 bug 的一半以上，且每次都表现为"逻辑看起来完全正确，但就是不对"。

| 我以为 | 实际 | 后果 |
|---|---|---|
| `event.getSource()` 会给出输入框节点 | 安卓 11+ 经常返回 `null` | 微信整块漏记 |
| `getRootInActiveWindow()` 能兜底 | 微信里同样返回 `null` | 兜底也失效 |
| 输入框节点 `isEditable()` 为真 | 有些应用（微信）返回 false | 节点被当成非输入框丢弃 |
| 输入框为空时 `getText()` 返回空、hint 单独给 | 小米笔记把 hint **通过 `getText()` 返回** | 提示文字被当成用户输入 |
| `isFocused()` 可靠 | 部分 ROM 会撒谎 | 焦点过滤可能反而不记 |
| `getApplicationLabel()` 能取应用名 | 安卓 11+ 包可见性限制下失败 | 界面显示包名 |
| `<receiver exported="false">` 只有 shell 能发 | **连 shell 都发不进去**（uid 不匹配被拒） | 诊断探针完全失效 |
| `renameTo()` 失败会抛异常 | 静默返回 false | 索引丢失，记录"看不见" |

**共性**：这些都是"框架文档里说得通、真机上不成立"的行为。

**应对方法（有效）**：

1. **先看原始数据，再改逻辑**。给应用加"原始事件环形缓冲"，把 `event.getType() + 包名 + 类名 + 文本`
   直接打出来。微信那次就是靠它一眼看出：事件里**一直带着完整文本**，而我把宝全押在节点上。
2. **不要用"再加一层兜底"来修**。我连续两轮都在放宽节点判定条件，方向是错的
   —— 因为节点根本拿不到。**当兜底越加越多时，说明对问题的理解是错的。**
3. **把假设写成断言**。"`你好呀我很.startsWith("你好呀我")`" 这条断言一跑就破除了
   我对"前缀延伸"的想当然。

## 三、时间花在哪：一个有欺骗性的统计

粗算这一晚：

| 阶段 | 大致占比 | 说明 |
|---|---|---|
| 打通 ADB 调试 | **~25%** | 配对码反复过期、adb 版本问题、MIUI 限制 |
| 定位真实根因 | ~20% | 但正因为有 logcat，这部分其实很快 |
| 写代码修 bug | ~10% | 真正的修复往往只有几行 |
| 写测试 + 被测试打脸 | ~20% | 我有 3 次是**测试期望写错**，不是代码错 |
| 与工具链搏斗 | ~15% | 构建脚本、PowerShell 怪癖、adb 限制 |
| 环境本身的问题 | ~10% | 代理、网络、版本不一致 |

**结论一**：**"改代码"从来不是瓶颈**。真正的修复基本都是几行。
时间全花在"搞清到底发生了什么"和"把环境弄通"上。

**结论二**：写测试的时间看着"浪费"，但至少三次避免了我把错误理解当成修复提交上去。

## 四、ADB 无线调试的坑（按踩到的顺序）

1. **配对码有效期极短**（几十秒）。"用户截图 → 我执行"必然失败，
   报错是 `protocol fault (couldn't read status message)`——看起来像协议不兼容，
   实际是**配对窗口已关闭**。最终解法是让用户在自己电脑上一条命令完成（零延迟）。
2. **PowerShell 管道传 stdin 给 `adb pair` 会失败**。`"配对码" | adb pair` 不会正确关闭
   stdin，adb 收不到 EOF。必须用 .NET 进程精确控制：写入后立即 `Close()`。
3. **adb 版本夹缝**：36.0.0 配对握手直接失败；29.0.6 又太旧、没有 `pair` 子命令。
   中途换 34.0.5 仍然失败——**最终证明不是版本问题**，是配对窗口过期。
   （教训：换版本前先确认失败原因，否则只是浪费时间下载。）
4. **`exported="false"` 连 shell 都发不进广播**。诊断探针第一版就是这么废掉的。
   正确做法：`exported="true"` + 应用内开关把门 + 明确文档说明。
5. **手机连的是电脑开的移动热点**（`<本机热点网段>`），这反而比同一 WiFi 更稳，
   不受路由器 AP 隔离影响。
6. **应用私有目录 `adb pull` 不到**（Android 11+），非 debuggable 应用也不能 `run-as`。
   所以要看应用内部状态，只能让**应用自己**把它打到 logcat（探针方案）。

## 五、构建链的坑（不用 Gradle 的代价）

选择"只用 SDK 自带工具"是对的（APK 56KB、无依赖、构建几秒），但代价是一堆细节：

| 坑 | 现象 | 解法 |
|---|---|---|
| `sources.txt` 带 BOM | javac 报"无效文件名" | 用 `UTF8Encoding($false)` 写文件 |
| lambda 引导方法缺失 | `找不到符号: 方法 metafactory` | `core-lambda-stubs.jar` 进 bootclasspath |
| d8 输出目录不存在 | `Invalid output` | 先 `mkdir` 再喂 d8 |
| PowerShell 把工具 stderr 当异常 | 明明成功却中断 | 不用 `$ErrorActionPreference='Stop'` |
| Java 注释里的 `\u` | "非法的 Unicode 转义" | 注释里不写 `\u` |
| `org.json` 是空实现 | 离线测试报 `Stub!` | 自研 `Json.java` |
| 多行字符串替换失配（CRLF） | 替换静默失败 | 单行锚点 + **改完必须 `grep` 验证** |

最后一条尤其重要：**我在这一晚有 4 次"以为改了、其实没改"**，
都是因为 PowerShell 的 here-string 用 LF、而工程文件是 CRLF。
后来养成习惯：每次批量替换后立刻 `Select-String` 确认。

## 六、测试策略：为什么值得

**离线可测的前提是"不依赖安卓 API"**。为此做了两次抽取：

1. `Json.java`：替代 `org.json`（它在 `android.jar` 里是空实现，一碰就 `Stub!`）
2. `PlainText.java`：把"是不是占位提示文字"的纯字符串判定从 `TypelogService` 里搬出来
   （服务类一加载就 `Stub!`，没法离线测）

**测试抓到的真问题**：

- 搜索的 `limit` 被当成"每文件"上限用 → 整个文件被跳过（有回归断言）
- 输入框标识用 `identityHashCode` → 同一段文字被重复记录
- 合并逻辑用 `startsWith` 判"改错别字" → 完全失效（有断言固化这个反例）

**测试也抓到了我自己的错误理解**（3 次）：

- 把"追加"当成"替换"（`你好呀我` → `你好呀我很` 是长度 4→5 的追加）
- 把"删字"当成"不算修改"
- 一度以为 `isEdit` 有 bug，实际是我的测试用例构造错了

> 结论：**测试最大的价值不是防止回归，而是逼你把模糊的直觉写成明确的断言**——
> 而模糊的直觉正是这类 bug 的温床。

## 七、失败与无效的尝试（同样值得记）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 用 `adb shell input text` 输入中文 | 失败 | adb 只支持 ASCII；更糟的是它触发了拼音输入法状态，把输入框搅乱（需要善后） |
| 生成二维码给手机扫 | 失败 | `adb` 命令行没有生成二维码的子命令，那是 GUI 工具的功能 |
| 用 `--v1-signing-enabled true` 得到 v1 签名 | 实际只有 v2/v3 | 不影响（minSdk 26 只需 v2） |
| 反复换 adb 版本解决配对失败 | 无效 | 真正原因是配对窗口过期 |
| 靠截图 + 口述定位问题 | 低效且误导 | 早期两次方向性误判都源于此 |

**关于"输不了中文"这条**：这是 `adb` 的硬限制，但它带来一个意外好处——
**迫使我用 ASCII 做通路验证、由用户做中文验证**，反而分清了"链路问题"和"编码问题"。

## 八、可复用的方法论（如果只记 5 条）

1. **先修调试通道，再修功能。** 黑盒调试的成本是白盒的十倍以上。
2. **遇到"逻辑正确但结果不对"，去读原始数据**，别改逻辑。
   加一个"把原始输入打出来"的开关，几乎总能一眼看穿。
3. **重复加兜底 = 理解错了。** 停下来问："我最核心的假设是什么？它一定成立吗？"
4. **把假设写成断言。** 纯逻辑抽出来，离线跑；测试写错也是收获（说明理解偏了）。
5. **每次修改后立刻验证是否真的生效**（`grep` 一下）。静默失败的修改会浪费时间在错误的前提上。

## 十、后半程新增的教训（消息分段那一段）

前 3 小时解决的是"能不能记到"，后 3 小时解决的是"记到的东西怎么分组"。这一段的教训更值钱。

### 1. 最值钱的一次修正来自用户的观察，不是我的推理

我的分段逻辑改了两轮，都在"用文本形态倒推是不是发送了"这个框架里打转：
共同开头长度 → 清空边界 → 又回到共同开头长度。每轮都自洽，每轮都不对。

用户一句话点破：**"我点击的是微信的发送，你是不是记录不到"**

一查：确实记录不到 —— 我的无障碍服务只订阅了 `typeViewTextChanged|typeWindowStateChanged`，
**按钮点击事件根本没订阅**。真信号一直摆在那里没采集，我却在用文本猜了整整两轮。

**教训**：当你在用**间接特征**推断某件事时，先问一句"这件事本身有没有直接的信号？"
如果有，采集它；如果没有，再退回推断。我连问都没问过。

### 2. 同一个坑会换个地方再踩一遍

修微信文本时发现：`event.getSource()` 返回 null，所以要退回读 `event.getText()`。
写完这条，紧接着写"发送按钮检测"，**我又只从节点读标签，忘了读事件文本** → 检测恒为 0。

**教训**：在一个平台上总结出的"某类 API 不可靠"，要当成**该类 API 的普遍性质**去检查所有用法，
而不是只修当前那一处。

### 3. 测试全绿 ≠ 行为正确（这次最深的体会）

第 9 项测试原来断言的是："清空重打应合并成一段"。**我把错误的行为当成正确行为固化了下来，
测试还通过了。** 这个 bug 一直活到用户在真实聊天里用出来。

**教训**：测试验证的是"实现符合我的理解"，不是"我的理解符合需求"。
当实现和预期一致却仍有用户抱怨时，问题在预期，不在实现。

### 4. "首条文本即占位"这类兜底，来自观察而非想象

小米笔记、B 站的输入框占位文字有两种给法：`getHintText()` 单独给，或直接当 `getText()` 返回。
后者从文本上无法与真实输入区分。但有一个可靠性质：**占位文字一定是该输入框的首条文本**。
于是"首条文本记为占位候选"就成了通用兜底。

**教训**：找不到"内容上"的判据时，去找"时序上"的判据。

### 5. 记录能力 > 分组精细度（取舍）

B 站的「发布」按钮**完全不产生点击事件**（推测是 Jetpack Compose 界面，按钮是 Canvas 单节点）。
所以那类应用拿不到提交信号，分段只能退回文本形态。

但用户自己给出了正确判断：**"这种的话毕竟都在 b 站上保存了"** ——
内容本身完整记录，只是分组可能粗一点，而平台侧也有草稿。

**教训**：分清"核心目的受损"和"体验精细度不足"。后者不该用引入系统级权限去换。

## 十二、第二轮（次日下午）：四个"静默失效"

第一轮的经验大多是"理解错了"，第二轮几乎全是**"工具安静地没生效"**。
这类问题比逻辑错误更贵，因为它让人在正确的地方反复怀疑自己。

### 1. 更新 APK 不等于代码生效

`adb install -r` 换掉了磁盘上的 APK，但**已绑定的无障碍服务继续跑旧 dex**。
它不是 Activity：更新不会重启它，系统也不会自动把它拉起来。

表现是致命的：**代码改了、装了、行为一点没变**。
我连续三次据此认为"新规则没起作用"，甚至去怀疑规则本身写错了。

> 教训：任何"改了却没反应"的时刻，第一件事是确认**跑的是不是新代码**，
> 而不是继续推理逻辑。给每次安装配一条"重启服务并确认已绑定"的固定动作。

### 2. `am force-stop` 会连带杀死无障碍服务

用它"重启应用"之后，服务不会自己回来，应用再也收不到任何事件 ——
看起来和"采集坏了"完全一样。**一个便利的调试命令，制造了两小时的假故障。**

> 教训：调试手段本身要有"副作用清单"。凡是用它做过的事，都要能回滚/复核。

### 3. 数据里没有的东西，离线分析会替你"猜"

分段依赖"哪个输入框"，但这个标识**从未存盘**，只在渲染时现算。
导出数据里没有它，于是我的离线脚本把所有记录当成同一个框 ——
**分析结论比应用本身更乐观**，两者不一致，而那个不一致正是唯一的线索。

> 教训：**导出数据的字段必须覆盖所有影响行为的输入**，
> 否则离线复现的偏差会伪装成"应用的 bug"。
> 反过来说：当离线分析与线上行为不一致时，先怀疑"分析缺了输入"，再怀疑逻辑。

### 4. 静默失效的开关，比报错的开关危险

本机 aapt2 **静默忽略** `--version-code` / `--version-name`：传与不传，产物逐字节相同。
结果整晚构建的所有包都是 `versionCode=1`，升级时系统认为"版本没变"，
排查时也无法从 `dumpsys` 判断装的是哪一版 —— 平白多绕一圈。

> 教训：**凡是被正确性依赖的属性，构建后都要断言**。
> 一个不报错的开关，等于不存在。

### 这一轮真正的修复（很小）

```java
// 存盘，而不是每次现算
r.field = fieldKey(...);
// 空值视为"同框"，保证与历史记录兼容
if (!cur.field.isEmpty() && !next.field.isEmpty() && !cur.field.equals(next.field)) return false;
// 构建后断言版本
if ($badging.Line -notmatch "versionCode='$VersionCode'") { throw ... }
```

四个陷阱，三处真正的代码改动加起来不到十行。
**时间和钱几乎全花在"确认到底发生了什么"上** —— 与第一轮的结论完全一致。

### 附加产出：把"看日志"变成脚本

这一轮新增了 4 个离线分析脚本（`show_day` / `find_splits` / `find_similar` /
`check_long_gap`）。它们的价值不在于算得多好，而在于**把"逐条翻手机"换成一条命令**——
手机上只能一条条看，电脑上能一眼扫完全貌。这与第一轮"先修调试通道"是同一条道理。

### 关于成本的一句话

用户提出"用免费网页版分析日志"。这其实是对的分工：
**大文件的内容分析不需要一个能改代码的助手**。
需要写代码、跑构建、读设备状态时才用贵的通道；纯看内容用免费的就够了。
把"贵的能力"用在只有它能做的事情上。

## 十三、第三轮：最危险的一类 bug 是"假正常"

这一轮的反馈全部来自用户实际使用，而且呈现出同一个模式：
**界面显示一切正常，实际已经在丢数据。**

| 用户原话 | 实际情况 |
|---|---|
| "系统的无障碍总开关是关的，但最上面显示采集状态是开启的" | `isServiceEnabled()` 只看"是否在启用列表里"，MIUI 停用后条目仍在 → 永远显示"正在记录" |
| "我现在开启无障碍了还是会说记录停了" | 服务确实没连上，但提示让人去找一个**该机型根本不存在**的总开关 |
| "新装的话无法保持无障碍状态吗" | 实测：安装不影响；**`am force-stop` 才会清掉** |

### 1. "假正常"比"报错"危险得多

报错会让人去查；"显示正常"会让人继续用，直到需要找回内容时才发现什么都没有。
这一轮的三次反馈全是这一类。

> 教训：**凡是"我在正常工作"的界面声明，都必须能被证伪。**
> 本项目的做法是把判断依据也显示出来（诊断里的"状态探测依据"一行），
> 而不是只给一个结论。

### 2. 一个"保险起见"的动作，反复破坏用户数据

为了"确保新代码生效"，我每次都执行 `adb shell am force-stop`。
实测它的副作用：

```
accessibility_enabled    1 → 0
enabled_accessibility_services   有 → 被删除
Bound services           已绑定 → {}
```

而 `install -r` **本身就会重启进程加载新代码**，force-stop 毫无必要。
于是"每次装新版用户都要重新开无障碍"这个反复出现的现象，
根因是我的调试习惯，而用户和应用背了这个锅。

> 教训：**给调试动作列"副作用清单"，并定期质疑它是否仍然必要。**
> 一个习惯性附加动作，会在几十次迭代里持续造成损失，而且没人会怀疑它。

### 3. 给用户的指引必须在这台设备上真实存在

我根据 `accessibility_enabled=0` 判断"总开关关着"，
让用户"到无障碍页打开最上面那个总开关"——而该 MIUI 版本的**无障碍页根本没有总开关**
（那个值只是"有服务被启用"的结果标志，不是可操作的控件）。
用户回复："我的手机没有总开关呀"。

> 教训：**写给用户的每一步，都要能在他手上的设备上指出具体位置。**
> 依赖一个"应该存在"的系统控件之前，先确认它存在。

### 4. 被误报的失败（CI）

CI 连续失败，显示 `Storage tests failed`，但真正原因是：
`tools/check_diag_fields.py` 里写死了 Windows 路径（形如 `X:\...\项目目录\...`），
在 Linux runner 上直接报错退出。**与存储测试毫无关系。**

> 教训：失败信息里的"哪个步骤"不一定等于"哪里错了"。
> 排查被误报的失败，先看**日志原文**，而不是步骤名。
> 同类问题这一晚出现了四次（aapt2 静默忽略参数、install 静默失败、
> 服务跑旧 dex、这个 CI 误报），共同点都是"报告与实际不一致"。

### 5. 补丁脚本的自我伤害

用脚本按花括号配对替换方法时，我几次把**字段声明**一起塞进替换块，
造成重复定义、反复返工（`已在类中定义了变量 SVC_*`）。
还出现过"删除步骤把自己刚插入的新方法删掉"（删除找的是第一处匹配）。

> 教训：**工具脚本的替换粒度要匹配职责**——
> 替换方法就只替换方法体，字段单独加；删除要指定出现位置，不能默认第一处。
> 这些都写进了 `tools/patch_java.py` 的用法约定。

### 6. 诊断能力是"眼睛"，不能顺手删

重构记录页时把诊断内容搬进弹窗，漏掉了六段，其中
**"最近 25 条原始事件"是解决本项目大多数硬 bug 的工具**。
用户直接指出："你不要删除功能呀这样你之后也不好诊断了呢！"

现在有 `tools/check_diag_fields.py`：扫描两个类里全部 41 个可诊断字段，
要求都能在诊断面板看到，缺失即失败，并已接入 CI。

> 教训：重构时"删除旧实现"必须**逐段对照旧代码迁移**，不能凭记忆写。

## 十五、第四轮：去抖、边界与分层

这一轮的起点是用户早上的一句反馈：
> "一个字一个字的输入「我 等 着 你 回 来」，最后的「来」不记录"

查下去牵出了三个 bug（其中两个是我自己修的代码引入的），
最后收敛到一条**通用原则**——而这条原则是被用户逼出来的：

> "不要用特例呀，这种通用的是不是很难呀"

### 1. 去抖期间，内存里那一版是**唯一副本**

写入走 350ms 去抖。发送会让输入框清空，而"清空"被当成删除，
在"忽略删除"设置下走这条路径：

```java
if (Prefs.ignoreDeletions(this) && added <= 0) {
    p.text = text;   // 把待写的「来」覆盖成空
    return;          // 从未落盘
}
```

**那一版永远消失了。**

> 教训：凡是持有"尚未持久化的状态"，**任何丢弃该状态的路径都必须先落盘**。
> 这类 bug 的特征是"偶尔丢最后一个动作"——正好是最难复现、也最容易被当成偶发的那种。

修法是加 `flushPending()`：在"要丢弃"之前先写掉。并在发送标记之前也调用一次，
保证**正文在前、边界在后**。

### 2. 我自己引入的：时间戳顺序倒挂

`markSendBoundary()` 在 flush **之前**取了 `now`，于是这条边界记录的时间戳
比它前面的正文还早 1 毫秒：

```
12:05:29.110  <了>     ← 正文
12:05:29.109  <>       ← 边界，比正文早
```

排序后边界插到了正文前面，分段判据"两条文本之间夹着一次提交"把正文算进了下一段。
**实测表现**：`<示例文本> 与 <示例文本啊>` 本该按前缀合并，却被切开。

> 教训：写两条**有先后关系**的记录时，后写的必须取**更晚**的时间戳。
> 顺序信息要么体现在时间戳里，要么体现在插入顺序里 —— 两边不一致就会互相打架。

### 3. 主 bug：过滤把分段依据丢掉了

用户实测："四句话直接给我合并成一句话了"。四条独立消息
（好 / 好不好 / 你不好 / 你不会）在界面上显示成一条，标注"合并 4 版"。

而同一份数据，探针 `bursts` 却显示 5 段。**同一个分段器、同一份数据，结果不同**
——说明差异在**输入**上：

```java
// refreshList() 交给分段器之前
if ("send".equals(r.ev) || r.text.isEmpty()) {
    continue;        // 把边界记录整条丢掉
}
```

被丢掉的两类恰恰是分段的**唯一可靠依据**：
- `ev="send"`：用户点了发送（真信号）
- 空文本：输入框被清空（几乎所有应用都有的结构性信号）

丢掉之后，分段器看不到任何边界，只能退回用**文本形态**去猜
（前缀、共同字、间隔）——而形态判据永远会漏，于是只能不断加特例。

> **教训：特例越加越多，是分层错了的信号。**
> 与其继续给判据打补丁，先问一句"我是不是把某个通用依据丢掉了"。

修法是一条规则而不是一个特例：

**过滤只作用于"显示"，不作用于"分段"。**

| 层 | 职责 | 边界记录 |
|---|---|---|
| 读取/过滤 | 按时间、应用、搜索词筛选 | **原样保留** |
| 分段 | 把版本归并成"话" | 作为**第一优先**判据 |
| 显示 | 逐条 / 合并视图 | 由 `groupNewestFirst` 排除空段 |

判据也改为按**证据强度**排序，而不是按文本形态：

1. 两条之间夹着发送标记（真信号）
2. 输入框被清空（结构性）
3. 换了输入框或应用（结构性）
4. 间隔过长（弱）
5. 以上都没有，才用文本形态兜底

### 4. 我的验证方法错了：走了自己方便的路

我先用探针看到"5 段"，就下结论说数据正常、等于**用自己方便的那条路否定了用户的观察**。

```
探针 bursts → 走【原始数据】     → 5 段
应用界面    → 走【过滤后的路径】 → 1 段  ← 用户看到的
```

> 教训：**验证必须沿"用户实际看到的那条路径"走。**
> 用自己的调试通道证明了什么，不等于用户那边是对的 ——
> 两条路径只要有一处不同，结论就可能相反。

### 5. 同一个错误犯了第二次：force-stop

文档第 12 节是我自己写的"永远不要 force-stop"，结果为了截图重启应用时**又用了它**。
后果：无障碍设置被清空，用户看到"应用故障"。

排查后确认**不是崩溃**（`logcat -b crash` 为空、数据完好），而是被强杀后
系统处于"服务声明存在但无实例"的中间态，MIUI 把它显示成故障。

> 教训：**写进文档的规矩，第一个要遵守的是写它的人。**
> 应该用 `am start` 把应用切到前台 —— 它不杀进程，也就不需要重启。

### 6. "让用户做真实操作，我做检测" —— 这一轮最好的协作方式

我试图用 `adb input` 复现"打完立刻发送"的竞态，试了两次都不行：
adb 每次调用启动 JVM 就要几百毫秒，永远慢过去抖的 350ms；
就算把输入和删除塞进同一次 `input` 调用，也控制不住输入焦点。

用户说："**要不我来弄 QQ 上的，你来检测**"。

结果一次就拿到了决定性证据：

```
flushes 2 → 9        抢救了 7 次（这些字在老版本会丢）
sendBoundaries 0 → 8  发送检测同时恢复
QQ 记录行数 106 → 125
```

> 教训：**有些场景（真实输入法、真实应用、真实手势）根本模拟不了。**
> 这时正确的分工不是"我想办法模拟"，而是
> **用户做他本来就会做的事，我把观测点准备好**。
> 前提是应用里得有可读的计数器 —— 这也是为什么诊断面板值得投入。

### 7. 顺带修的两件事

- **判据 11 增加子串排除**：`你好` → `好`（"好"是"你好"的真子串）不再被判成"整词重打"，
  而 `甲苹果` → `乙苹果`（互不为子串）仍然合并。这是回答用户
  "如果我发个跟上文不同的单字会怎样"时发现并修掉的。
- **测试调用位置**：新增的用例被放在汇总打印**之后**，导致打印的项数不含它们。
  加测试时要确认它真的被计数。

## 十六、第五轮：隐私与边界

起点是使用者一句半开玩笑的话：

> "你怎么把我本地路径都上传了，哈哈哈，you不要这样子啦"

接着补了一句更关键的：

> "还有 md 文档里面"

**这两句话让我把整个仓库重新审了一遍，而顺着查下去，问题比"路径"严重得多。**

### 1. 隐私不只是密钥，还有"环境"和"内容"

我原先以为"不提交密钥文件"就够了。实际泄露的三类：

| 类别 | 例子 | 我原先有没有意识到 |
|---|---|---|
| **环境信息** | 磁盘路径、用户名、机器名、内网 IP、设备型号 | 部分意识到 |
| **内容** | 直接引用使用者打过的字（购物草稿、聊天片段） | **完全没意识到** |
| **凭据** | 构建脚本里写死的密钥库口令 | **完全没意识到** |

第三类最严重：`release.ps1` 和 `build-apk.ps1` 里各有一个口令默认值。
密钥**文件**没入库，但**口令在公开仓库里** —— 谁拿到文件就能签名。

### 2. 一次泄露往往是成簇的，要顺藤摸瓜

排查顺序（每一步都是被前一步引出来的）：

```
用户指出路径泄露
  → 清理路径时顺手审计凭据
      → 发现两个密钥库口令
  → 给"路径"写护栏（通用模式 + gitignored 令牌表）
      → 护栏立刻抓到 __pycache__/*.pyc 里的残留路径
  → 用户续指"还有 md 文档里面"
      → 扫文档里的 <...> 引用
          → 又发现源码注释、测试文件、README 示例 JSON 里也有
```

> 教训：**发现一个隐私问题时，不要"改完这一个就收工"。**
> 同一批工作习惯往往同时留下了好几类痕迹。

### 3. 审计要用模式扫，不能靠记忆

我第一轮只查了"自己能想到的类别"（路径、IP、机器名），于是漏掉了内容引用。
第二轮换了方法 —— **按结构特征扫**：

```powershell
# 文档里所有 <...> 形式的引用例子
Select-String -Pattern '<[^<>
]{2,40}>'
```

一次就把 6 处真实内容全列出来了。
**按"数据来源/结构"扫，比按"我记得写过什么"扫可靠得多。**

### 4. 护栏自己有两个坑

写 `check_private_paths.py` 时踩到：

**坑一：护栏不能含真实信息。**
如果我把"某个人的用户目录具体叫什么"写进护栏，护栏自己就成了泄露源。
做法：**只用通用模式** —— 描述"用户目录前缀 + 任意用户名"这类**结构**，
而不是某个人的真实名字；真实的私有字符串登记到
`tools/.private-tokens`（已 gitignore）。

**坑二：护栏会扫到自己。**
那些通用模式字符串就写在护栏文件里，扫描时必然命中自己。
做法：把护栏自身加入排除名单 —— 这不是放宽标准，那些是**模式**而非真实路径。
（写这段说明时我又踩了一次：把模式原文抄进文档，于是文档被护栏判为泄露。
所以这里只描述结构，不抄模式。）

### 5. "源码清了"不等于"清干净了"

护栏抓到 `tools/__pycache__/*.pyc` 里**仍然残留着旧的绝对路径** ——
源码里的字串删掉了，编译产物里的字节码还带着。
`.pyc` 不该入库（没有理由提交编译缓存），已移除并加入忽略。

### 6. 口令可以改，密钥不能换 —— 这条决定了处置方式

发现口令泄露后，第一反应容易是"那就换个密钥吧"。**不能这么做**：

| | 改口令 | 换密钥 |
|---|---|---|
| 私钥 | **不变** | 变了 |
| 证书指纹 | **不变** | 变了 |
| 已装应用能否覆盖升级 | **能** | **不能**，必须卸载重装 |
| 后果 | 无 | **本机所有记录丢失** |

安卓判断"是否同一个作者"看的是**证书指纹**，与口令无关。
所以正确处置是**改口令**：泄露的口令立即失效，而升级链路不受影响。

改完必须验证两件事：
1. 旧口令确实失效
2. **证书指纹没变**（我用手机上已装应用的指纹做对照：`F7:17:48:D9...`）

只看"命令执行成功"是不够的 —— 那只能证明命令跑了，不能证明东西没坏。

### 7. 公开仓库里的"默认值"就是公开的口令

```powershell
[string]$StorePass = 'draftguard'    # ← 这一行等于把口令公开
```

构建脚本不该给口令设默认值。改成按优先级取：
环境变量 → `keystore.properties`（已 gitignore）→ 交互输入。
顺带附一份 `.example` 说明格式。

### 8. 换示例文字必须保持它演示的"结构性质"

把文档里引用的真实内容换成合成例子时，我第一轮换错了：

```
原例：在设置里搜的那两个词    共同开头 = 0   ← 这正是"整词打错重打"的判据依据
我换成：示例词汇甲 → 示例词汇乙   共同开头 = 4   ← 与注释自相矛盾
```

**示例不只是"随便一段文字"，它承载着要说明的性质**（长度、共同开头、分叉位置）。
换的时候要连续两次问："这个例子的技术含义是什么？我的新例子还成立吗？"

### 9. 同一个疏忽第三次出现：只看输出最后一行

提交前我看护栏的输出，只看了最后一行"处理办法…"，没注意前面是 `❌`，
于是**在护栏失败的状态下提交了**。

这和之前的两次是同一个毛病：
- 只看 CI 的步骤名（"Storage tests failed"）不看日志，误以为是存储测试的问题
- 只看 `adb install` 有没有报错，没验证版本是否真的变了

> 已经能把"验证"写成清单了：
> **① 看完整输出，不看最后一行 ② 验证结果是"东西没坏"，不是"命令跑了" ③ 沿用户实际看到的路径验证**

### 这一轮的数字

| | |
|---|---|
| 清理文件 | 8 个文档/脚本 + 3 个 `.pyc` |
| 替换处数 | 路径/标识 ~40 处，真实内容 75 处 |
| 更换口令 | 2 个密钥库，指纹均未变 |

### 一句话

> **公开仓库里的每一个字符串都在"替使用者说话"。**
> 路径在说他的磁盘布局，示例文字在说他的输入内容，默认口令在说他的密钥。
> 写文档时想的是"这个例子很清楚"，没想到它同时也是**别人的隐私**。
