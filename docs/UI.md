# 界面设计与实现

三个页面、纯代码搭布局（不依赖 androidx）。这份文档记录**设计取舍**与**实现坑**——
后者每一条都对应一次真实的返工或用户反馈。

代码：`android/java/com/draftguard/MainActivity.java`、
布局骨架：`android/res/layout/activity_main.xml`

---

## 一、整体结构

```
┌──────────────────────────────┐
│  记录  │  应用  │  工具        │  ← 导航栏固定在顶部，不随内容滚动
├──────────────────────────────┤
│  FrameLayout：三个页面互斥显示  │
└──────────────────────────────┘
```

**为什么不用 Fragment**：项目一直不用 androidx，Fragment 会引入依赖；
页面只有三个，`View.setVisibility` 互斥足够。切页时按需刷新该页内容。

## 二、三个页面各放什么（与用户逐项确认过）

| 页面 | 内容 | 设计理由 |
|---|---|---|
| **记录** | 顶部一行摘要 → 搜索框 → [时间范围][看逐条][更多] → 记录列表 | **打开就看到记录**。原先 4 张诊断卡 + 12 个按钮铺了 4 屏，记录埋在最后 |
| **应用** | 图标 + 名称 + 包名/天数/最近时间 + 条数；点进去看该应用全部历史（按天分组） | 按"哪个应用"找内容比按时间找更自然 |
| **工具** | 采集状态 / 实时预览 / 统计 / 今天记录过的 App；可折叠的**设置**与**诊断** | 诊断与设置是"出问题时才看"的，不该占首屏 |

**按钮从 12 个收成 3 个 + 「更多」**：导出、分享、设置与诊断、清除都进「更多」。

## 三、记录条目怎么渲染

**用 `ListView` + 适配器，不是把几百段拼进一个 `TextView`。**
早期版本把 918 段拼成一个字符串塞进一个 `TextView`，结果是：

- 一整面**文字墙**，长文本（实测最长 228 字）与下一段糊在一起，没法逐段阅读
- 没有视图回收，条目一多就卡

现在每行是「图标 + 应用名 + 时间/字数/合并版本数 + 正文」的圆角卡片，
由 `ListView` 回收复用。

**列表刷新时保留滚动位置**：记住 `getFirstVisiblePosition()` 与首个可见项的相对偏移，
`notifyDataSetChanged()` 后用 `setSelectionFromTop()` 还原 ——
否则每次事件到达都会把用户拽回顶部。

## 四、图标

- 用 `PackageManager.getApplicationIcon(pkg)` 取真实图标
- **不需要额外权限**：清单里的 `<queries>`（MAIN/LAUNCHER）已让这些包可见
- 后台批量加载 + 内存缓存；取不到时用**字母兜底图标**：
  取应用名首字，底色由包名散列决定（同一应用每次颜色一致）
- 兜底在实测中确实用到了（`com.android.htmlviewer` 没有启动图标）

## 五、视觉

| 项 | 取值 | 说明 |
|---|---|---|
| 页面底色 | `#0D0F14` | 压暗，才能让卡片浮起来 |
| 卡片底色 | `#232833` | 早期用 `#1A1D26` 与页面几乎分不出，看不出是卡片 |
| 正文 / 次要 / 强调 | `#E8ECF3` / `#8B95A7` / `#5B9DFF` | 只用三种前景色，靠**字号**做层次而不是靠颜色 |
| 圆角 | 12–14dp | 卡片统一 |
| 卡片间距 | 列表的**透明 divider** 高度（10dp） | 见下面第 6.2 条 |

## 六、实现坑（每条都返工过）

### 6.1 刷新滚动位置上方的卡片，会把用户正在看的内容顶走

事件到达时重写顶部卡片 → 卡片高度变化 → 下方内容整体位移 →
用户看到的是"界面自己跳回了统计区"。截屏也会触发（窗口事件走同一条刷新路径）。

**做法**：刷新前判断卡片是否**完整可见**（ScrollView 的 `[scrollY, scrollY+height]`
与 view 的 top/bottom 比较），不可见就跳过并记下"欠一次刷新"，滚动时补上。

> 滚动位置是对用户的承诺；任何改变它**上方**内容高度的操作都会破坏这个承诺。

### 6.2 `ListView` 会覆盖 item 自己的 `LayoutParams`

给行视图设 `margin` **完全无效**（`AbsListView` 会替换成自己的 LayoutParams），
卡片会挤成一整块。改用**列表的 divider 高度**制造间距，
外层留白用 `setPadding` + `setClipToPadding(false)`。

### 6.3 刷新逻辑要放在"知道状态"的地方

诊断卡片原先由 `refreshTools()` 填充，而它只在切页或事件到达时执行 ——
展开诊断后一直停在"读取中…"。填充应该在 `buildDiagBox()` 里，
因为只有它知道"是否展开、视图是否已建"。

> 如果一次刷新可能"没人调用"，它迟早会没人调用。

### 6.4 异步弹窗类设置要在回调里重建

`chooserRow` 点击后立刻重建列表，但"最少记录字数/保留天数"是弹窗里选的、异步生效 ——
重建时拿到的还是旧值，表现是"改完不刷新，要再点一次才变"。
把重建交给选择完成后的回调。

### 6.5 一处关注点只留一个入口

设置文案、设置应用、诊断正文各自同时存在于"工具页"与"弹窗"两处。
写成两份时，迁移页面**默默丢了六段诊断内容**。现在收敛为
`settingItems()` / `applySetting()` / `diagText()` 三个共用方法。

### 6.6 折叠只重建本区块

设置/诊断折叠时若整页重建，一展开就跳回页顶。
折叠只重建自己的容器（`settingsBox` / `diagBox`），并单独更新标题箭头。

### 6.7 界面上写的范围，代码必须真的按那个范围查

按钮写着「全部时间」，而 refreshList() 只读了 store.readDay(今天) ——
标签承诺了代码没做的事。用户看到的是「我明明有前几天的记录，这里却只有今天的」。

现在真的遍历所有日期，并且**非今天的条目会带上日期**（如 10-09 00:39），
否则昨天的记录只显示时间会让人以为就是今天的。

> 凡是界面措辞在描述「范围、状态、数量」，都要回到代码确认它真的成立。
> 这与「假正常」是同一族问题：界面说的和实际做的不一致。

### 6.8 按钮要放在它作用的对象**上方**

早期布局先把结果卡片加入、按钮行后加入，于是结果一长（实测 9000+ 字符），
用户要滚过整屏文字才能点到「时间范围 / 筛选应用」。
用户原话："能把按钮移到文字上面吗，不然还要翻一大堆才能看到按钮"。

现在是：状态 → 搜索 → 按钮 → 结果，并且点「看全部记录」后**自动滚到按钮区**。

> 可操作的东西要排在内容之前；内容可以很长，操作不该被它挤走。

### 6.9 卡片要跟着数据走，否则显示的是"启动那一刻的真相"

用户反馈"这个软件不记录"。查下来记录一直在写，问题在**统计卡片只在 `onResume` 刷新** ——
打开应用那一刻读一次，之后记录在涨、卡片不动，看起来就像什么都没记。

现在统计卡片跟着采集服务的广播刷新（节流 2 秒），并且：
- 没有记录时明确写"当前没有任何记录"，而不是留一排 0
- 区分两套数字：**"本次会话落盘"**（服务重启会归零）与 **"今天落盘版本数"**（磁盘上的历史总量）

> 与 6.7 同族：界面显示的数字必须与背后的事实同步。
> 一个停在过去的数字，会让用户得出完全相反的结论。
