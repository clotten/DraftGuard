## 一、方法论（如果只记五条）

| # | 一句话 | 出处 |
|---|---|---|
| 1 | **先修调试通道，再修功能。** 黑盒调试的成本是白盒的十倍 | RETRO 一 |
| 2 | **"逻辑对但结果不对"时，去读原始数据，别改逻辑** | RETRO 二 |
| 3 | **重复加兜底 = 理解错了。** 停下来问"我最核心的假设是什么" | RETRO 八 |
| 4 | **把假设写成断言。** 纯逻辑抽出来离线跑，一秒出结果 | RETRO 六 |
| 5 | **每次改动后立刻验证是否真生效。** 静默失败的修改会让人在错误前提上浪费时间 | RETRO 五 |

## 二、三天三轮，问题性质完全不同

| 轮次 | 性质 | 典型 |
|---|---|---|
| 一 | 我**理解错了** | 以为 `getSource()` 总能拿到输入框节点 |
| 二 | 工具**静默失效** | 装了没生效（服务跑旧 dex）、参数被忽略（aapt2 版本号） |
| 三 | 界面**假正常** | 显示"正在记录"，实际在丢数据 |

> **共同解法只有一条：让系统自己说出真相。**
> 原始事件日志、状态探测依据、构建后版本断言、可离线复现的分析脚本。

## 三、最危险的一类 bug：假正常

报错会让人去查；**"显示正常"会让人一直用，直到需要找回内容时才发现什么都没有**。

实测到的三次：
- `isServiceEnabled()` 只看"是否在启用列表里"，系统停用后条目仍在 → 永远显示正常
- 提示用户去打开一个**该机型根本不存在**的总开关
- 诊断说"日志未开启"，实际是无障碍服务被关掉了

> 凡是"我在正常工作"的界面声明，都必须**能被证伪**。

## 四、操作红线

| 不要做 | 后果 |
|---|---|
| `adb shell am force-stop <本应用>` | **清空无障碍设置**（enabled=0 + 从启用列表删除），应用再也收不到事件 |
| 依赖内存里的状态去解读历史数据 | 同一份数据在不同时刻解读不同（曾导致 1039 个版本一段都没合并） |
| 在异步操作**开始**时就重建界面 | 显示的是旧值 |
| 告诉用户去找一个"应该存在"的控件 | 该 MIUI 无障碍页根本没有总开关 |

**要做的**：改完代码用 `adb install -r`（它本身就会重启进程），并确认绑定状态。

## 五、这个项目的技术要点

| 主题 | 一句话 | 详细 |
|---|---|---|
| 采集 | 无障碍服务是系统里唯一能读别的应用输入框的正规通道；节点常拿不到，**事件自带文本更可靠** | TROUBLESHOOTING 1 |
| 存储 | 存**完整快照**而不是按键增量：丢一次写入只是少一版，绝不会把文字拼错 | ARCHITECTURE |
| 分段 | 12 条判据、10 个阈值；**"点了发送"是最可靠的分段信号**，且必须落盘 | SEGMENTATION |
| 界面 | 首屏就该是内容；诊断信息收进独立页面；用 `ListView` 而不是拼字符串 | UI |
| 测试 | 把纯逻辑抽成普通类（`Json`/`PlainText`/`SendBoundary`/`Burst`），69 项断言跑在普通 JVM 上 | ARCHITECTURE |
| 构建 | 不用 Gradle，SDK 自带工具链即可；**构建后必须断言产物版本** | PROJECT_STATE 七 |

## 六、几条"我以为 vs 实际"

| 我以为 | 实际 |
|---|---|
| `event.getSource()` 会给出输入框节点 | 安卓 11+ 经常返回 `null` |
| 输入框为空时 `getText()` 返回空、hint 单独给 | 小米笔记把提示语**直接当 `getText()` 返回** |
| `exported="false"` 只有 shell 能发广播 | **连 shell 都发不进去**（uid 不匹配） |
| `renameTo()` 失败会抛异常 | 静默返回 `false` |
| aapt2 的 `--version-code` 会生效 | **静默忽略**，产物一直是清单里的旧版本号 |
| `ListView` 里 item 的 `margin` 会生效 | 被 `AbsLayoutParams` 覆盖 |

## 七、第四轮补充（去抖 / 边界 / 分层）

| # | 一句话 | 出处 |
|---|---|---|
| 1 | **过滤只作用于"显示"，不作用于"分段"。** 边界记录（发送标记、空文本）是分段的依据，不能在过滤阶段丢掉 | SEGMENTATION §八 |
| 2 | **特例越加越多，是分层错了的信号。** 先问"我是不是把某个通用依据丢掉了" | SEGMENTATION §八 |
| 3 | 持有"尚未持久化的状态"时，**任何丢弃它的路径都必须先落盘** | RETRO 十五 |
| 4 | 写两条有先后关系的记录，**后写的必须取更晚的时间戳** | RETRO 十五 |
| 5 | **验证要走用户实际看到的那条路径** —— 用自己方便的通道证明什么，不等于用户那边是对的 | RETRO 十五 |
| 6 | **写进文档的规矩，第一个要遵守的是写它的人** | TROUBLESHOOTING §15 |
| 7 | 有些场景模拟不了（真实输入法、真实应用）。这时正确分工是：**用户做他本来就会做的事，我准备好观测点** | RETRO 十五 |
| 8 | 判据要按**证据强度**排序：发送标记 > 输入框清空 > 换框/换应用 > 间隔 > 文本形态 | SEGMENTATION §八 |
| 9 | 加测试时要确认它**真的被计数**（新用例曾被排在汇总打印之后） | RETRO 十五 |

### 遇到"偶尔丢最后一个动作"这类 bug

先问三个问题：
1. 这个状态是不是**只存在于内存里**（还没落盘）？
2. 有哪些路径会**丢弃**它？
3. 丢弃之前，**有没有先落盘**？

第四轮的丢字 bug 就是这三问的答案全是"是/有/没有"。

## 八、第五轮补充（隐私与凭据）

| # | 一句话 |
|---|---|
| 1 | **隐私不只是密钥**：环境信息（路径/用户名/机器名/内网 IP）与**内容**（引用使用者真实输入）同样算 |
| 2 | **一次泄露往往是成簇的** —— 顺藤摸瓜，别"改完这一个就收工" |
| 3 | 审计**按结构特征扫**（如所有 `<...>` 引用），不靠"我记得写过什么" |
| 4 | 护栏自己不能含真实信息（否则它成为泄露源），也不能扫自己（自我引用必误报） |
| 5 | **源码删了不等于清干净**：`.pyc` 字节码里会残留绝对路径 |
| 6 | **口令可以改，密钥不能换**：改口令指纹不变→能升级；换密钥指纹变了→要卸载丢数据 |
| 7 | 改完口令要验证**两件事**：旧口令失效 + **证书指纹未变** |
| 8 | 公开仓库里的"默认值"就是公开的口令 —— 凭据不设默认值 |
| 9 | 换示例文字要**保持它演示的结构性质**（长度/共同开头/分叉位置） |
| 10 | 别只看输出的最后一行（护栏失败却提交了） |

### 提交前的三条自查

```
① 看完整输出，不看最后一行
② 验证"东西没坏"，而不只是"命令跑了"
③ 沿用户实际看到的那条路径验证
```

### 凭据类问题的处置顺序

```
1. 先判断泄露的是【口令】还是【密钥本身】
2. 口令 → 改口令（指纹不变，升级不受影响）
   密钥 → 只能换密钥，但必须接受"卸载重装、数据丢失"
3. 改完立刻验证：旧口令失效 + 证书指纹未变
4. 留一个带旧口令的本地备份当逃生口（绝不入库、绝不上传）
5. 确认所有敏感文件都在 .gitignore 里，逐条用 check-ignore 验证

## 九、给未来的自己

- **诊断能力是眼睛，重构时不能顺手删**（曾经丢过六段，其中"最近 25 条原始事件"是排查利器）
- **重构时逐段对照旧代码迁移，不能凭记忆写**
- **失败信息里的"哪个步骤"不一定等于"哪里错了"**（CI 显示 Storage tests failed，真因是脚本里的 Windows 路径）
- **用户每次说"不对"都指向真问题** —— 三天里没有一次误报
